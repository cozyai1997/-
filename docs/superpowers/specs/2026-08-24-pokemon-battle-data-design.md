# 포켓몬 전투 데이터 확장 설계

- 작성일: 2026-08-24
- 상태: 사용자 승인 설계를 문서화함
- 적용 대상: Pokemon Trainer Manager 웹 애플리케이션
- 기준 프로필: Cobbleverse 1.7.42 / Cobblemon 1.7.3

## 1. 목적

보유 포켓몬을 등록하고 확인할 때 다음 정보를 정확하고 혼동 없이 제공한다.

1. 테라타입을 한국어로 선택하고 목록·최종 확인·상세 화면에서 확인한다.
2. 선택한 종과 폼이 거다이맥스 가능한지 자동 판정하고, 가능한 경우에만 해당 개체의 거다이맥스 인자 보유 여부를 기록한다.
3. 선택한 기술의 기본 PP를 선택 직후뿐 아니라 최종 확인과 상세 화면에서도 확인한다.
4. 폼별 종족값, 개체값, 노력치, 현재 레벨의 실제 능력치를 같은 표에서 구분해 보여준다.
5. 기존 사용자 데이터는 임의로 바꾸거나 삭제하지 않는다.

## 2. 확정한 제품 규칙

### 2.1 테라타입

- 일반 포켓몬은 18개 일반 타입과 `스텔라`를 합친 19개 테라타입 중 하나를 선택할 수 있다.
- 테라타입을 모르는 기존 개체와 신규 입력을 위해 `미지정`을 허용한다.
- 오거폰은 폼/마스크에 따라 풀·물·불꽃·바위 중 하나로 제한한다.
- 테라파고스는 스텔라로 제한한다.
- 스텔라는 일반 방어 타입 상성표의 타입이 아니므로 기존 `reference_types`에 넣지 않는다. 별도의 테라타입 기준 테이블을 사용한다.

### 2.2 거다이맥스

- `거다이맥스 가능`은 종 단위가 아니라 현재 폼 단위로 판정한다.
- 원천데이터의 34개 거다이맥스 폼과 대응되는 32개 종을 사용한다.
- 스트린더의 하이/로우키, 우라오스의 일격/연격을 서로 다른 폼 관계로 처리한다.
- 나옹 지역폼, 피카츄 코스튬처럼 같은 종 안의 다른 폼을 종 단위로 잘못 허용하지 않는다.
- 자동 판정은 그 종/폼에 거다이맥스 형태가 존재하는지 나타낸다. 실제 보유 개체가 거다이맥스 인자를 가졌는지는 사용자가 별도 체크한다.
- 불가능한 폼에서는 체크 입력을 비활성화하고 값은 항상 `false`로 저장한다.

### 2.3 PP

- 표시값은 전투 도중 남은 PP가 아니라 기술의 기본 최대 PP다.
- 표기는 `기본 PP: 15`로 통일한다.
- 원천값이 없는 기술은 `기본 PP: 확인 불가`로 표시한다.

### 2.4 능력치 용어

화면에는 다음 문구를 그대로 사용한다.

- **종족값 Base Stats**: 그 포켓몬 종과 폼 자체가 가진 기본 능력치
- **개체값 IV (원본)**: 태어날 때 정해지는 0~31 수치
- **노력치 EV**: 전투나 아이템으로 올리는 훈련 수치, 능력치당 최대 252
- **실제 능력치 Stats**: 현재 레벨에서 실제 전투에 적용되는 HP·공격·방어·특공·특방·스피드 숫자

현재 데이터 모델의 원본 개체값과 왕관 보정 적용값은 다음처럼 명확히 표시한다.

- `개체값 IV (원본)`: 태어날 때 결정된 값
- `적용 IV (왕관 보정 포함)`: 실제 능력치 계산에 사용하는 값

## 3. 데이터 원천과 정규화

### 3.1 원천 파일

- 폼과 종족값: `Cobbleverse_Pokemon_Manager_Package_v1.3_TABLE_FIX/cobbleverse_data_full/forms_full.csv`
- 세부 폼과 aspects: `full_data_cache/pokemon-by-slug/<species>.json`
- 성격 보정: `cobbleverse_data/natures.csv`
- 기술 PP: `cobbleverse_data_full/moves_full.csv`
- 한국어 스텔라 명칭: `full_data_cache/ko_kr.json`

현재 원천에는 폼 1,498개가 있다. 기본 폼 1,025개는 모두 유효한 종족값을 가지며, 파생 폼 중 261개는 자체 종족값을 가진다. 나머지 212개 파생 폼의 0 값은 실제 0이 아니라 기본 폼 상속을 뜻하므로 게시 전에 상속을 해소한다.

### 3.2 기준데이터 검증

가져오기 단계에서 다음을 검사한다.

- 6개 종족값이 모두 1~255 범위인지 확인한다.
- 0 값 폼은 `baseFormId`를 따라가 유효한 값을 상속한다.
- 상속 대상 누락, 순환 참조, 일부 능력치만 0인 행을 거부한다.
- `battleOnly`, 원본 aspects와 거다이맥스 대상 관계를 보존한다.
- 성격의 상승/하락 능력치가 지원하는 5개 비-HP 능력치인지 검사한다.
- 신규 보유 포켓몬으로 선택 가능한 활성 폼마다 허용 테라타입 관계가 최소 1개 존재하는지 검사한다.
- 거다이맥스 관계의 양쪽 폼이 같은 종이며 대상이 battle-only 거다이맥스 폼인지 검사한다.

## 4. 데이터베이스 설계

### 4.1 `reference_forms` 확장

다음 열을 추가한다.

- `base_hp`, `base_attack`, `base_defense`
- `base_special_attack`, `base_special_defense`, `base_speed`
- `is_battle_only boolean not null default false`

레거시 게시본을 보존하기 위해 종족값 열은 스키마상 nullable로 추가하되, `모두 null` 또는 `모두 1~255`만 허용하는 CHECK를 둔다. 활성 게시본 검증은 1,498개 폼 모두에 완전한 값을 요구한다.

### 4.2 `reference_tera_types`

19개 테라타입을 담는 별도 기준 테이블을 만든다.

- `id`, `publication_id`, `identifier`, `name_ko`, `sort_order`, `is_active`
- 18개 일반 타입은 필요 시 `reference_type_id`로 연결한다.
- 스텔라는 `reference_type_id = null`이다.
- 인증 사용자는 읽기만 가능하고 게시 작업은 service role만 수행한다.

### 4.3 `reference_form_tera_options`

폼별 허용 테라타입 allowlist를 저장한다.

- 일반 플레이 가능 폼: 19개 관계
- 오거폰: 해당 마스크 타입 1개 관계
- 테라파고스: 스텔라 1개 관계
- battle-only 폼은 신규 보유 포켓몬 선택지에서 제외한다.

이 관계는 UI 필터와 서버 저장 검증에서 같은 기준으로 사용한다.

### 4.4 `reference_form_gigantamax_options`

플레이 가능한 원본 폼과 대응 거다이맥스 폼의 관계를 저장한다.

- `publication_id`, `source_form_id`, `gigantamax_form_id`
- 동일 관계 중복을 금지한다.
- 일반 폼은 원본 aspects에서 `gmax`를 제거한 뒤 일치하는 폼에 연결한다.
- 스트린더와 우라오스의 폼 차이를 aspects로 보존한다.
- 마휘핑은 장식 폼 전체가 공통 거다이맥스 형태를 사용할 수 있도록 명시적인 예외 규칙으로 연결한다.

### 4.5 `owned_pokemon` 확장

- `tera_type_id uuid null references reference_tera_types(id)`
- `has_gigantamax_factor boolean not null default false`

직접 테이블 변경과 RPC 모두 다음 무결성을 지켜야 한다.

- `tera_type_id`가 있으면 현재 폼의 허용 테라타입이어야 한다.
- `has_gigantamax_factor = true`이면 현재 폼에 거다이맥스 관계가 있어야 한다.
- 종/폼 변경으로 관계가 무효가 되면 UI와 서버가 값을 `null` 또는 `false`로 조정한다.
- 생성·빠른 수정·보호 정보 정정 RPC는 특성·기술과 함께 한 트랜잭션에서 처리한다.

## 5. 거다이맥스 관계 생성 규칙

1. `forms[].aspects`에 `gmax`가 있는 폼을 대상 폼으로 분류한다.
2. 대상 aspects에서 `gmax`를 제거한다.
3. 같은 종의 플레이 가능 폼 중 남은 aspects가 일치하는 폼을 원본으로 선택한다.
4. 빈 aspects는 기본 일반 폼에만 연결한다.
5. 스트린더와 우라오스는 남은 폼 aspects로 각각 정확한 형태를 연결한다.
6. 마휘핑은 검증된 장식 폼 전부를 공통 거다이맥스 폼에 연결한다.
7. 관계가 없거나 둘 이상으로 모호하면 게시를 중단하고 오류를 보고한다.

문자열에 `gmax`가 포함됐는지만 보고 런타임에서 판정하지 않는다.

## 6. 실제 능력치 계산

실제 능력치는 현재 레벨, 선택 폼의 해결된 종족값, 적용 IV, EV, 현재 성격 보정을 사용한다.

- HP: `floor(((2 × 종족값 + IV + floor(EV / 4)) × 레벨) / 100) + 레벨 + 10`
- HP 외: `floor((floor(((2 × 종족값 + IV + floor(EV / 4)) × 레벨) / 100) + 5) × 성격 보정)`
- 상승 성격은 1.1, 하락 성격은 0.9, 무보정은 1.0이다.
- 껍질몬의 HP는 입력과 관계없이 1로 표시한다.
- 계산에 필요한 종족값이나 성격 데이터가 불완전하면 추정 숫자를 만들지 않고 `계산 불가`와 원인을 한국어로 표시한다.

## 7. 화면 설계

### 7.1 등록 마법사

- 3단계 특성 영역 아래에 `테라타입` 선택을 배치한다.
- 같은 영역에 `거다이맥스 가능/불가능` 배지를 표시한다.
- 가능한 폼에서만 `이 개체는 거다이맥스 인자 보유` 체크박스를 활성화한다.
- 4단계와 5단계에 능력치 용어 안내를 제공한다.
- 선택 폼의 종족값은 읽기 전용으로 표시한다.
- 5단계에서 레벨·적용 IV·EV·성격에 따른 실제 능력치를 즉시 계산해 보여준다.
- 6단계 기술 선택 상세에는 `기본 PP`를 독립된 정보로 강조한다.
- 7단계 최종 확인에 테라타입, 거다이맥스 인자, 실제 능력치, 기술별 기본 PP를 표시한다.

### 7.2 보유 포켓몬 목록과 상세

- 목록 카드에 테라타입 배지와 거다이맥스 인자 배지를 표시한다.
- 상세 헤더에도 같은 배지를 표시한다.
- 상세 화면에는 다음 열의 능력치 표를 제공한다.
  - 능력치 이름
  - 종족값 Base Stats
  - 개체값 IV (원본)
  - 적용 IV (왕관 보정 포함)
  - 노력치 EV
  - 실제 능력치 Stats
- 현재 기술과 목표 기술을 카드로 표시하고 이름·타입·분류·위력·명중·기본 PP·한국어 설명을 제공한다.
- 빠른 수정에서 테라타입과 거다이맥스 인자를 변경할 수 있다.
- 종/폼 보호 정보 정정 시 두 값도 새 폼 기준으로 재조정하고 감사 이력에 포함한다.

### 7.3 능력치 계산기

- 기존 `최종` 열 이름을 `실제 능력치 Stats`로 변경한다.
- 상단에 네 가지 능력치 용어 안내를 추가한다.
- 기존 수동 계산 기능은 유지한다.
- 껍질몬 HP 예외를 공통 계산 함수에 반영해 등록·상세·계산기가 같은 공식을 사용한다.

## 8. 오류 처리와 하위 호환

- 기존 보유 포켓몬은 `테라타입 미지정`, `거다이맥스 인자 없음`으로 유지한다.
- 기존 종·폼·특성·기술·IV·EV 데이터는 자동 변경하지 않는다.
- 과거에 battle-only 폼으로 저장된 행은 삭제하지 않고 상세에서 계속 볼 수 있게 한다. 신규 등록 목록에서는 제외하고 사용자가 보호 정보 정정으로 일반 폼을 선택할 수 있게 한다.
- 필터 읽기 실패 시 기존의 제한된 자동 재시도와 수동 `다시 불러오기` 흐름을 유지한다.
- 폼 변경 중에는 테라타입·거다이맥스·특성·기술 정합화가 끝날 때까지 저장 버튼을 비활성화한다.
- 서버가 허용하지 않는 직접 요청은 전체 트랜잭션을 실패시키며 부분 저장을 남기지 않는다.

## 9. 보안과 성능

- 새 public 기준 테이블은 RLS를 활성화하고, 플랫폼 기본 ACL까지 명시적으로 회수한다. `anon`은 읽을 수 없고 `anon`/`authenticated` 모두 INSERT·UPDATE·DELETE·TRUNCATE·REFERENCES·TRIGGER 권한이 없어야 한다.
- authenticated에는 정확히 활성 기준데이터 SELECT 정책만, service role에는 게시 권한만 부여한다. 카탈로그 postflight가 세 테이블의 RLS·정책명·역할·조건과 실제 권한을 실행 가능하게 검증한다.
- 보유 포켓몬 RLS는 기존 `auth.uid() = user_id` 소유권 규칙을 유지한다.
- 폼·테라타입 및 폼·거다이맥스 관계 조회를 위한 복합 인덱스를 둔다.
- RPC는 `search_path`를 고정한다. 옵션 게시의 구 2인수 RPC는 존재하지 않아야 하고, 인증 digest/version을 받는 4인수 교체 RPC에는 service role만 EXECUTE할 수 있다.
- 스텔라는 일반 타입 상성 테이블에 넣지 않아 기존 18×18 상성 324행을 보존한다.

## 11. 배포 순서와 복구

1. 기준데이터와 DB 동작을 로컬 테스트에서 먼저 검증한다.
2. 애플리케이션 커밋을 GitHub에 푸시하고 clean local `HEAD`가 원격 branch SHA와 정확히 같은지 확인한다.
3. 동일 active version의 기존 수량을 확인하고, 검토된 단일 마이그레이션만 dry-run한 뒤 추가 열·기준 테이블·RLS·RPC를 적용한다.
4. core write 직전에 전역 옵션 staging이 0임을 확인한다. 같은 version에 fresh authenticated core SQL과 동일 후보의 옵션 데이터를 차례로 게시하고 exact count/digest/RLS/catalog postflight를 검증한다.
5. 옵션 게시가 실패하면 publisher가 자신이 생성한 caller-owned exact batch만 정리하고 전역 staging 0을 증명한다. 운영 절차는 batch 수나 version으로 소유권을 추정하지 않으며 unidentified residue를 삭제하지 않고 진단 상태를 남긴 뒤 중단한다. DB는 partial-core 상태로 기록하며 배포하지 않는다. 같은 고정 SHA·후보·원천을 다시 인증한 경우에만 재시도하고 전체 postflight를 반드시 다시 수행한다.
6. cached-auth Vercel CLI로 기존 canonical deployment ID/URL을 고정하고 fresh production build를 `--skip-domain`으로 staged 배포한다. 같은 원격 SHA를 담은 `meta.releaseCommit`, project/team, `READY`를 검증한다.
7. canonical alias가 여전히 이전 ID인 상태에서 staged URL의 일회성 사용자 흐름과 6종 cleanup residue 0을 검증한다. 그 동일 staged ID만 promote하고 canonical identity를 확인한다. 승격 이후 실패하면 고정한 이전 ID로 rollback한다.

새 보유 포켓몬 열에는 안전한 기본값을 사용하므로 기존 행은 유지된다. UI 배포가 실패하면 Vercel canonical만 고정한 이전 deployment로 되돌리고 DB의 하위 호환 열과 게시 데이터는 유지한다. 이미 기록된 사용자 데이터를 삭제하는 롤백은 수행하지 않는다.
